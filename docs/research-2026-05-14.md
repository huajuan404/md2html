# Markdown → Human-Optimized HTML 工具调研与产品方向草案

日期：2026-05-14  
阶段：研究 / 需求访谈前，不进入实现  
灵感源：`/Users/doing/Desktop/content_professor/lib/karpathy-html-llm-output/主帖与回复整理.md`

## 1. 灵感帖给出的核心判断

Karpathy 主帖的关键点不是“把 Markdown 渲染成 HTML”，而是：AI 输出正在从纯文本 → Markdown → HTML → 更高带宽的交互式视觉媒介演进。HTML 的价值在于布局、图形、交互、信息密度和分享能力。

高赞回复里同时暴露了风险和机会：

- 机会：HTML 更适合视觉输出、教学、报告、仪表盘、可交互解释器。
- 风险：HTML 可能 2-3x 增加输出 token/生成成本；图表和视觉呈现会增强“看起来是真的”的错觉；协作评论、发布、版本管理仍缺失。
- 现有尝试：有人做 agent skill（`html-anything`）、artifact 分享平台（`artifact.land`）、可编辑 AI HTML 文档（`html-docs.com`）、日报 broadsheet、模板+数据标准（`canvakit`）。

## 2. 竞品/开源实现分层

### A. 传统 Markdown 编辑器：双栏、实时、导出已经成熟

| 产品/项目 | 能力 | 对我们的启发 | 不足 |
|---|---|---|---|
| StackEdit | 浏览器 Markdown 编辑器、滚动同步、云同步、发布为 Markdown/HTML/模板输出 | 双栏编辑、Scroll Sync、发布集成是成熟交互基线 | 输出仍是 Markdown 的线性渲染 |
| Dillinger | Monaco 编辑器、实时预览、导出 Markdown/Styled HTML/PDF、拖拽文件、本地自动保存 | 顶栏功能、文件导入、HTML/PDF 下载可以直接借鉴 | “styled HTML”不是信息重组 |
| MarkdownLab | 左编辑右预览、上传、Mermaid、KaTeX、代码高亮、自包含 HTML/PDF 导出、离线本地优先 | 很接近基础 MVP 的工程形态 | 仍是 Markdown faithful render，不是 AI/设计化重组 |
| Editor.md | CodeMirror+jQuery+Marked，可嵌入、表格/代码/TeX/流程图/序列图 | 如果要快速嵌入老派编辑器可参考 | 技术栈老，视觉和现代产品体验弱 |
| MarkText / Typora 类 | WYSIWYG、主题、HTML/PDF 导出 | 证明用户接受“源文档即预览” | 更偏写作工具，不解决 AI 输出的信息设计 |

结论：**“左 Markdown / 右 HTML / 实时预览 / 下载”没有技术稀缺性。差异化不在编辑器，而在“语义理解 + 信息重组 + 视觉表达”。**

### B. AI HTML / Artifact 平台：证明“HTML 作为 AI 输出对象”正在成形

| 产品/项目 | 能力 | 对我们的启发 | 不足 |
|---|---|---|---|
| Claude Artifacts | 独立窗口中生成、查看、迭代、下载单页 HTML/React/SVG/Markdown 等 | Artifact 是正确的输出心智：内容是可复用对象，不是聊天气泡 | 闭源、平台内体验；不是专门的 Markdown→HTML 产品 |
| artifact.land | 交互式 artifact 的社区/分享空间 | 分享、发现、fork、浏览器可运行内容是后续方向 | 不负责 Markdown 源编辑与转换 |
| HTML Docs | 把 Docs/Slides/网页/AI artifacts 变成可编辑、可评论、可发布 HTML | “HTML 也需要 Google Docs 式评论协作”是强需求 | 更像 HTML 文档协作平台，不是本地 Markdown 编译器 |
| Canvakit | 模板+数据源声明，重新拉数据即可重渲染，无需重新发 HTML | 很适合未来把 Markdown 拆成 `source + IR + template` | 目前是标准/规范方向，不是完整终端产品 |

结论：**Artifact 方向是趋势，但现有平台缺少“Markdown 源可控 + 本地导出 + AI 信息设计”的一体化工作流。**

### C. AI/Skill/Renderer：最接近“信息重组”的已有肩膀

| 项目 | 能力 | 对我们的启发 | 不足 |
|---|---|---|---|
| html-anything | Codex/Claude Code skill；任何文件/URL/数据源→漂亮、交互、单文件 HTML；自动 source/style routing；17 套具体设计系统 | 最接近你的灵感：style 不是 CSS 皮肤，而是页面结构、组件词汇、交互模型 | agent skill 形态，不是实时双栏编辑器；用户不能在 Markdown 左栏持续编辑并即时看到重组结果 |
| WeMD / md-beautify | 本地优先 Markdown 公众号排版；GFM/表格/代码/数学公式；十余主题；自定义 CSS；一键复制 | 主题系统、公众号/中文内容排版、CSS 设计器值得借鉴 | 面向公众号排版，重样式，弱信息重组 |
| MarkNest | Markdown workspace → PDF；Mermaid/Math、主题、自定义 CSS、WASM、本地/CLI、安全、离线资产 | 离线、本地、安全、相对路径/图片/批量工作区处理值得借鉴 | 主目标 PDF，不是视觉化 HTML 重组 |
| Markweavia / HTMLSlides 类 | Markdown → HTML slides/presenter | “同一 Markdown 变成 slides/sequence”是可选渲染模式 | 限于演示文稿，不是通用报告/网页 |

结论：**html-anything 可以作为设计系统和 prompt/route 参考；MarkdownLab/StackEdit/Dillinger 作为编辑器基线；HTML Docs/artifact.land 作为发布协作愿景；Canvakit 作为未来 IR/模板方向。**

## 3. 有没有现成产品能直接满足？

目前没有一个产品完整满足以下组合：

1. Markdown 文件上传/粘贴；
2. 左侧源文档持续编辑；
3. 右侧实时预览；
4. 右侧不是普通 Markdown 渲染，而是人类友好的信息重组；
5. 可选择压缩方式/主题/展示形态；
6. 下载本地单文件 HTML；
7. 可本地优先运行，后续再考虑发布/评论/分享。

最接近的拼图：

- 基础编辑器：MarkdownLab / Dillinger / StackEdit。
- 信息重组范式：html-anything。
- Artifact 分享协作：HTML Docs / artifact.land。
- 模板化长期架构：Canvakit。

因此建议不是从零发明 Markdown 编辑器，而是做一个 **“Markdown-to-Information-HTML compiler”**：Markdown 只是源，HTML 是经过信息设计的传播介质。

## 4. 建议的产品定义

一句话：

> 一个本地优先的 Markdown → Human-Optimized HTML 转换器：左侧编辑/上传 Markdown，右侧实时生成面向人类阅读、理解、传播的结构化 HTML 页面，并支持一键下载。

### MVP 应该包含

- 输入：粘贴 Markdown、上传 `.md/.markdown/.txt`。
- 编辑：左侧 CodeMirror/Monaco Markdown 编辑器，自动保存。
- 预览：右侧 sandbox iframe，实时刷新。
- 渲染模式：
  - Faithful：普通 Markdown 渲染，作为对照与 fallback。
  - Reader：长文阅读，目录、摘要、重点、边注。
  - Brief：信息压缩，结论卡、要点、证据、行动项。
  - Dashboard：从表格/列表/数字中抽取指标、卡片、队列。
  - Slide/Carousel：把段落变成可分享序列。
- 顶部选项：主题、密度、渲染模式、是否启用 AI 重组、导出 HTML。
- 导出：单文件 HTML（内联 CSS/JS，默认不依赖外部 CDN）。
- 安全：sanitize Markdown HTML、iframe sandbox、默认禁远程脚本。

### 非 MVP / 第二阶段

- 评论协作、发布链接、artifact gallery。
- 多文件项目/工作区。
- 自定义模板市场。
- LLM style auto-routing 和多轮设计迭代。
- HTML 反向更新 Markdown。

## 5. 推荐技术路线

### 不加新依赖前的概念架构

```text
Markdown source
  -> parser(AST: headings/tables/lists/code/quotes)
  -> semantic extractor(document map, claims, tables, entities, metrics)
  -> transform IR(page intent: reader/brief/dashboard/slides)
  -> renderer(template + theme tokens)
  -> sandboxed preview iframe
  -> single-file HTML export
```

### 可能的技术选型

- 前端：Vite + React 或 Svelte。
- 编辑器：CodeMirror 6（轻量、现代）或 Monaco（Dillinger 风格，更重）。
- Markdown：unified/remark/rehype 或 markdown-it/marked。
- 图表：MVP 可先用 CSS/SVG，避免图表依赖；后续再加 Observable Plot / ECharts。
- AI 层：先设计为可选 provider；MVP 可以先做规则式 IR，后续接 OpenAI/Claude/本地模型。
- Export：生成完整 HTML 字符串，内联 CSS/JS，Blob 下载。

## 6. 关键产品取舍

1. **实时 vs AI 重组成本**：每次敲字都调 LLM 不现实。建议实时分两层：规则式实时；AI 重组手动点击或 debounce 后后台刷新。
2. **美观 vs 可验证性**：必须保留“源 Markdown / 抽取证据 / 生成 HTML”链路，避免漂亮页面掩盖错误。
3. **主题皮肤 vs 信息结构**：主题只改颜色字体是不够的；模式要改变页面结构和阅读路径。
4. **本地优先 vs 发布协作**：MVP 本地优先；发布协作后置。
5. **通用转换器 vs 特定场景**：建议先服务 AI 输出/研究笔记/长文/报告，而不是一开始覆盖所有 Markdown。

## 7. 下一轮需求访谈的核心问题

第一版必须先定“主杀伤场景”。建议三选一：

A. AI 输出美化器：把 ChatGPT/Claude/Codex 的长 Markdown 答案变成可读/可分享 HTML。  
B. 研究笔记发布器：把长文、线程、资料整理变成文章/简报/知识页。  
C. 通用 Markdown 工具：先做 Dillinger/MarkdownLab 的本地优先增强版，再逐步加 AI 重组。

我的建议：选 **A + B 的交集**，也就是“AI/研究输出 → 人类友好 HTML”。这样最贴近 Karpathy 讨论，也最能避开普通 Markdown 编辑器红海。

## 9. 追加产品核心：Markdown 是可编辑源，HTML 是消费投影

用户补充后的核心差异化：这个产品不是又一个 Markdown previewer，也不是一次性 HTML artifact 生成器，而是要解决 HTML 的最大结构性痛点：

> HTML 对人类阅读、消费、传播非常友好，但对非开发者的增量编辑非常不友好；Markdown 则天然适合人类修改。因此产品的核心应是：人类持续编辑 Markdown，系统持续把它投影为更高带宽、更好消费的 HTML。

这意味着产品架构必须坚持：

1. **Markdown 是 canonical source of truth**  
   用户真正维护的是 Markdown，不是 HTML。HTML 可以下载、分享、发布，但不是主要编辑对象。

2. **HTML 是 projection，不是源文件**  
   HTML 由 Markdown + 语义 IR + style renderer 生成。即使 HTML 很复杂，也必须能从源 Markdown 重新生成。

3. **实时编辑是核心体验，不是附属功能**  
   左侧 Markdown 的每次修改都应该尽快反馈到右侧 HTML。普通规则式渲染可实时；AI/LLM 级重组可 debounce、手动刷新或分层缓存。

4. **需要 source map / block map**  
   右侧每个主要 HTML 区块应能追溯到左侧 Markdown 的段落、标题、表格或列表范围。否则后续无法支持“点右侧卡片，定位左侧源文案”。

5. **AI 修改也应落回 Markdown patch，而不是直接改 HTML**  
   如果未来加入“帮我把这一节更适合 CEO 阅读”“压缩这一段”“把这个表格变成洞察卡”等语义编辑，AI 的产物应该优先是 Markdown patch 或结构化 IR patch，而不是直接重写 HTML。

6. **设计系统要可扩展，但主链路要稳定**  
   新输入类型、新 style、新渲染模式都应该只是扩展 parser/extractor/renderer，而不能破坏 Markdown → AST → semantic IR → render plan → HTML 的主链路。

### 架构含义

建议把系统拆成五层：

```text
Editable Markdown Source
  -> Markdown AST + source positions
  -> Semantic IR / document model
  -> Render Plan / information design plan
  -> Style Renderer
  -> HTML Projection + source map
```

其中：

- **Markdown AST** 负责忠实解析用户输入。
- **Semantic IR** 负责理解内容：标题层级、论点、证据、表格、行动项、引用、代码、数字等。
- **Render Plan** 负责决定“这份内容应该怎样被人类消费”：长文、简报、仪表盘、卡片流、slide、学习页等。
- **Style Renderer** 负责视觉系统：字体、布局、组件、密度、色彩、交互。
- **Source Map** 负责让 HTML 视觉块和 Markdown 源文本保持可追踪关系。

### 产品定位更新

新的定位应改成：

> 一个 source-first 的 Markdown-to-HTML information compiler。它让人继续用 Markdown 做增量编辑，但让最终消费对象变成经过信息设计的 HTML 页面。

这比“Markdown 转 HTML”更准确，也比“AI 生成 HTML”更可维护。

### 9.1 已确认的一版架构原则：source map 是核心技术，不是后置增强

确认结论：source map / block map 应作为第一版核心技术底座实现。

原因：产品的本质不是一次性生成漂亮 HTML，而是让 HTML 成为 Markdown 的可追溯消费投影。没有 source map，右侧 HTML 会逐渐变成“漂亮但失控”的结果；有 source map，系统才能保持可编辑性、可定位性、可增量更新和未来 AI patch 能力。

第一版原则：

> 任何主要 HTML 视觉节点都必须尽可能声明它来自哪些 Markdown source blocks。

建议最小数据结构：

```ts
type SourceBlock = {
  id: string
  type: 'heading' | 'paragraph' | 'list' | 'table' | 'code' | 'quote'
  startLine: number
  endLine: number
  raw: string
}

type RenderNode = {
  id: string
  kind: 'hero' | 'section' | 'card' | 'table' | 'timeline' | 'quote' | 'summary'
  sourceBlockIds: string[]
  html: string
}
```

建议 HTML 输出保留内部映射属性：

```html
<section data-render-node="node-7" data-source-blocks="block-12 block-13">
  ...
</section>
```

第一版 UI 可以不暴露复杂 source map 功能，但内部必须生成和携带映射。后续可自然扩展：

- 点击右侧区块，左侧跳到源 Markdown。
- 悬停右侧区块，左侧高亮来源。
- 左侧局部修改，只刷新右侧相关 render nodes。
- AI 针对右侧区块的修改最终落回 Markdown patch。
- 导出 HTML 时可选择保留或去除 `data-source-*` 元信息。

## 10. 完整线程复核后的竞品校准

详见：`docs/thread-tools-research-2026-05-14.md`。

新结论：市场已经快速出现相邻产品，尤其是 `nexu-io/html-anything`、`Nimbalyst`、`HtmlDrag`、`AgentDocs`、`visual-explainer`、`html-artifacts` 等。

最重要校准：

- `nexu-io/html-anything` 已经非常接近 agentic HTML editor：左输入、右 preview、模板/skill、多 surface、一键导出、本地 agent CLI、diff-edit。
- 但公开资料和代码快速检查未见 block-level source map / `SourceBlock` / `data-source-blocks` / click-back Markdown source 机制。
- 因此我们的差异化必须更明确：不是泛化 HTML artifact 生成，而是 **source-mapped Markdown projection editor**。

更新后的产品护城河：

> Markdown 是 canonical editable source；HTML 是 regenerated projection；source map 是核心桥梁；AI 修改应优先落回 MarkdownPatch / IRPatch，而不是 HTML patch。
